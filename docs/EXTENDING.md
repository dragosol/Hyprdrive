# Adding a setting is adding a row

This is the contract the settings app is built on, and it is the reason the app
is four QML files rather than one per pane: **a new option is one row of data.**
No new component, no new dialog, no new write path, no new revert story. This
document says exactly what a row is, what each pane does with one, what the
apply-strategies mean, and then walks through a row that was actually added this
way — commit `de174db`, `wallpaper.interval`, end to end.

If you are adding an option and find yourself writing QML, something is wrong
with either the row or this document. Say which.

---

## 1. Where rows come from

`docs/schema.json` is generated by `scripts/gen_schema.py` and is what the app
reads. It joins three sources, and **only one of them is hand-written**:

| source | where | how many | who maintains it |
| --- | --- | --- | --- |
| `plugin` | `Config.cpp`, parsed by `scripts/lib/configkeys.py` | 79 | the plugin. Add a key there and the row appears. |
| `hyprland` | `config/schema/hyprland-descriptions.json`, a snapshot of `hyprctl descriptions -j` | 353 | refresh with `gen_schema.py --refresh-hyprland` |
| `curated` | `config/schema/curated.json` | 13 | **you**, by hand |

The first two are mirrors, and `make all` runs `gen_schema.py --check` so a
mirror that has drifted is a build failure rather than an option nobody can
reach. The third — `curated.json` — is where panes, routes, per-key overrides
and everything that is not a compositor option live. **A new setting that is not
a Config.cpp key or a Hyprland option is a row in `curated.json`'s `extra` list.**

---

## 2. What a row is

```json
{
  "key": "wallpaper.interval",
  "pane": "wallpaper",
  "type": "int",
  "widget": "slider",
  "apply": "none",
  "default": 15,
  "min": 1,
  "max": 240,
  "description": "Minutes between slideshow changes. ..."
}
```

| field | required | meaning |
| --- | --- | --- |
| `key` | yes | The identity. For a compositor option it IS the option path (`decoration:blur:size`); for a plugin key it is `plugin:hyprdrive:` + the path; for an ii knob it is `ii:` + the dotted path into ii's `config.json`; for anything else it is a name of your choosing with a dot in it. It is also what the theme importer matches against, so an option whose key is its real Hyprland path is importable for free. |
| `pane` | yes | Which pane draws it. Must be an id in the `panes` list or `gen_schema.py` fails. |
| `type` | yes | `bool` `int` `float` `string` `color` `vec2` `path`. Decides how a value is rendered into Lua (`hdctl.lua_value`) and how the importer compares old to new (`hdimport.same_value`). |
| `widget` | no | `switch` `slider` `number` `choice` `color` `text` `path`. Defaults are derived from the type and the presence of `min`/`max`/`choices`. |
| `apply` | yes for curated | How a change becomes real. See §4. |
| `default` | yes | What the row shows before anything has written it. |
| `min`, `max` | no | Slider bounds. Also what makes a numeric row a slider instead of a number box. |
| `choices` | no | A fixed dropdown. Omit it for a dropdown whose contents are runtime data (see §5). |
| `description` | yes | The sentence under the key. Write it for somebody who has not read the code. |
| `locked` | no | A refusal, with the reason as its value. The row shows the value and will not write it — through the UI *or* through a theme import. Used for `decoration:blur:enabled`, which the product rule says is not a casual toggle. |
| `derived` | no | This key is written by theme-sync from the wallpaper's palette. The row's badge then says *inherited* until somebody sets it, and *pinned* after — because setting a derived key IS pinning it (Phase 10). |
| `follows` | no | Documentation only: "`-1` means follow this other key". |
| `note` | no | Extra prose under the row. |

Overrides for a **generated** row (a plugin key or a Hyprland option) go in
`curated.json`'s `overrides` map, keyed by the full key. Same fields.

## 3. What each pane does with a row

There is **one** row component (`SchemaRow.qml`) and **one** generic pane
(`SchemaPane.qml`). Everything below is what already happens; none of it is
per-pane code.

| pane | how it gets its rows | what else it draws |
| --- | --- | --- |
| Hyprland, Blur, Dock, Overview, Quickshell | `Hd.entriesFor(pane)` — every row whose `pane` matches | a filter box once there are more than 12, and a raw-snippet editor if the pane has a `fragment` |
| Monitors | not rows at all: `hdmon list`, one block per output, `monitor_fields` from `curated.json` | the keep-these-settings countdown |
| Wallpaper | `Hd.entriesFor("wallpaper")` minus the two the pane draws itself | the repository dropdown and the picture grid |
| Profiles | none | the snapshot log, saved profiles, the import preview |

So: put a row on `hyprland`, `blur`, `dock`, `overview` or `quickshell` and it
appears with **no other change anywhere**. Put one on `wallpaper` and it appears
in the Slideshow section. `monitors` and `profiles` are not row-driven; a row on
either is a mistake `gen_schema.py` will not catch.

## 4. Apply-strategies

`apply` names the mechanism that turns a written value into a running one.
`hdctl.set_one` dispatches on it, and that dispatch is the **single write verb**
in the product — the UI does not branch on source, and neither does the theme
importer, and neither does a profile restore.

| `apply` | what `hdctl set` does | when to use it |
| --- | --- | --- |
| `reload` | writes the value into the pane's fragment through `fragment.py` (machine half only, raw block preserved), then `hyprctl reload` | anything the compositor reads: every plugin key and every Hyprland option |
| `qs-restart` | writes ii's `config.json`, coercing to the type already there | `ii:` keys. Quickshell watches its own file for most of them; the ones read at construction need the restart, which `hdprof` fires when it sees ii's file move |
| `wallpaper` | runs `scripts/hyprwall-rotate.sh` with `WALL=` and `THEME=` from the `wallpaper.theme` row | wallpaper paths, still or video |
| `monitor` | goes through `hdmon apply` and its fifteen-second countdown | anything that can take away the screen you would undo it with |
| `none` | stores the value and stops | settings that are read by something else on its own schedule — the slideshow's mode and interval, read by `hdwall tick` on every tick |

Two things that are deliberately *not* apply-strategies:

- **`preview`** is not durable and is not reachable from `set`. It is a live
  one-shot the compositor forgets on the next reload; the slider drag uses it and
  letting go commits. Phase 10 measured both reasons it cannot be a write: a
  live value is discarded by the next `hyprctl reload` (theme-sync issues one on
  every wallpaper change) and it lands *after* the config parse, so it would beat
  a pin — and pin > derived > default is the only ordering the fragment layer
  has.
- **`live`** does not exist. See above.

### Bulk, and the snapshot

`hdctl bulk KEY=VALUE ...` writes many rows behind **one** `hdprof.snapshot_before`
and **one** reload. Three sites call that same function — a theme import, a bulk
apply, a monitor change — because those are the three changes too big to undo
from memory. If you add a fourth kind of many-at-once change, call
`hdprof.snapshot_before` and `hdprof.finish`; do not invent a second snapshot.

## 5. Dropdowns whose contents are runtime data

`choices` is a fixed list in the schema. When the options are data — the wallpaper
repositories, the modes of an output — the row carries `"widget": "choice"` with
**no** `choices`, plus a `dynamic_choices` string naming where they come from, and
the pane fills the dropdown itself. `wallpaper.repo` is the example:
`"dynamic_choices": "hdwall repos"`, and `WallpaperPane.qml` builds the model from
`Hd.wallRepos`.

This is the one case where a row does need a line of QML, and it needs it in the
pane that already knows about that data. Adding a *repository* is still not a
schema change: repositories are data, and only the setting that chooses between
them is a row.

## 6. Worked example: `wallpaper.interval`, end to end

Added in commit `de174db`. In full, this is what it took.

**One row** in `config/schema/curated.json`, in the `extra` list:

```json
{
  "key": "wallpaper.interval",
  "pane": "wallpaper",
  "type": "int",
  "widget": "slider",
  "apply": "none",
  "default": 15,
  "min": 1,
  "max": 240,
  "description": "Minutes between slideshow changes. The timer wakes once a minute and reads this, so a change takes effect immediately and nothing has to be restarted."
}
```

**One command:**

```
$ python3 scripts/gen_schema.py
wrote docs/schema.json -- 445 entries (79 plugin, 353 hyprland, 13 curated) over 7 panes
```

That is the whole change to the settings surface. What it bought, with nothing
else written:

- the row draws on the Wallpaper pane as a slider from 1 to 240, with its
  description under the key and a *set* badge once it has been written;
- `hdctl set wallpaper.interval 1` writes it, and `hdctl get`/`schema --live`
  reads it back out of the store because its apply-strategy is `none`;
- `hdctl bulk` can carry it with a dozen others behind one snapshot;
- **the theme importer** can set it, because the importer maps onto schema keys
  and does not know what a wallpaper is;
- **a profile snapshot** carries it, because the store is part of the config
  surface, and `hdprof revert` puts it back;
- **`hdwall tick`** reads it through `setting("wallpaper.interval", 15)`, which
  is a store lookup with the schema default as the fallback — so a machine where
  nobody ever touched the row still has a working slideshow interval.

The only code written for that row was the two lines in `hdwall.py` that *use*
it, which is the point: the setting existed the moment the row did, and the code
that consumes it is the code that would have to exist anyway.

**What would have made it more than a row.** A new pane (a `panes` entry plus a
QML file, if it is not row-driven), a new apply-strategy (a branch in
`hdctl.set_one` and a row in §4), or a widget that does not exist yet (a
component and a line in `SchemaRow`'s selector). Everything else is one row.

---

## 7. Checklist

1. Row in `config/schema/curated.json` — or a key in `Config.cpp`, or a refreshed
   Hyprland snapshot.
2. `python3 scripts/gen_schema.py`.
3. `make all` — `gen_schema.py --check` is one of its four checks, so a schema you
   forgot to regenerate is a red build.
4. Nothing else, unless §6's last paragraph applies.
